# Расширение `YAXUNIT_ERPUH` — юнит-тесты модулей ERP.Управление холдингом

Расширение конфигурации 1С с юнит-тестами общих модулей конфигурации
**ERP.Управление холдингом** (ERPUH). Тесты написаны на фреймворке
[YAxUnit](https://github.com/bia-technologies/yaxunit): движок тестирования —
в соседней папке `exts/yaxunit`, тесты — здесь.

Расширение не заимствует объекты конфигурации: оно только добавляет собственные
общие модули с тестами. Поэтому оно независимо от движка, ставится рядом с ним
и не конфликтует с обновлениями ERPUH.

## Состав

| | |
|---|---|
| Расширение | `YAXUNIT_ERPUH`, назначение — дополнение, префикс объектов `ОМ` |
| Тестируемые модули | общие модули конфигурации ERP.Управление холдингом: `ОбщегоНазначения`, `ОбщегоНазначенияКлиентСервер`, `СтроковыеФункцииКлиентСервер` |
| Тестовые модули | `ОМ_ОбщегоНазначения` — 5 наборов, 31 тест, 51 проверка; `ОМ_ОбщегоНазначенияКлиентСервер` — 17 наборов, 127 тестов, 436 утверждений; `ОМ_СтроковыеФункцииКлиентСервер` — 6 наборов, 43 теста, 128 утверждений |
| Покрытие | `ОбщегоНазначения` — 29 из 211 экспортных методов (14%); `ОбщегоНазначенияКлиентСервер` — 60 из 108 (56%); `СтроковыеФункцииКлиентСервер` — 26 из 29 (90%) |
| Прогон | 51 / 51, 127 / 127 и 43 / 43 PASSED, отчёты в формате Allure |
| Проверка честности | инверсия ожиданий — по каждому модулю 100% проверок красные (0 зелёных) → восстановление → снова PASSED |

Спецификация тестов (требование → шаги «дано / когда / тогда» → проверки) —
[`docs/modules/ОбщегоНазначения.md`](docs/modules/ОбщегоНазначения.md),
[`docs/modules/ОбщегоНазначенияКлиентСервер.md`](docs/modules/ОбщегоНазначенияКлиентСервер.md) и
[`docs/modules/СтроковыеФункцииКлиентСервер.md`](docs/modules/СтроковыеФункцииКлиентСервер.md).

## Требования

- 1С:Предприятие 8.3.27 (режим совместимости расширения — 8.3.27), интерфейс на русском языке;
- расширение с движком `YAXUNIT` из этого же репозитория (`exts/yaxunit`) — без него тесты не запускаются;
- база с конфигурацией ERP.Управление холдингом. Тесты серверные и в информационную базу не пишут,
  достаточно демонстрационной базы; данные ИБ в тестах не используются.

## Установка

### Исходниками в EDT

1. Открыть в EDT проекты `exts/yaxunit` и `exts/yaxunit_erpuh` (в том же workspace, где проект основной
   конфигурации).
2. В `exts/yaxunit_erpuh/DT-INF/PROJECT.PMF` в свойстве `Base-Project` указать имя проекта основной
   конфигурации в вашем workspace.
3. Обновить конфигурацию базы данных — оба расширения установятся в базу.

### Собранными `.cfe`

Собрать расширения штатными средствами (EDT или конфигуратор) и подключить к базе, например
через `ibcmd`:

```bat
ibcmd infobase config import --db-path=<база> --extension=YAXUNIT      <каталог конфигуратора yaxunit>
ibcmd infobase config import --db-path=<база> --extension=YAXUNIT_ERPUH <каталог конфигуратора yaxunit_erpuh>
```

Порядок подключения значения не имеет: движок и тесты независимы, тесты вызывают общие модули
движка (`ЮТест`, `ЮТТесты`, `ЮТАлюр`…) как модули соседнего расширения.

## Запуск тестов

1. Убедиться, что в базе подключены оба расширения — `YAXUNIT` (движок) и `YAXUNIT_ERPUH` (тесты).
2. Запустить тесты штатным для YAxUnit способом — внешней обработкой запуска тестов, с отбором
   по расширению `YAXUNIT_ERPUH` и нужному тестовому модулю (`ОМ_ОбщегоНазначения`,
   `ОМ_ОбщегоНазначенияКлиентСервер`, `ОМ_СтроковыеФункцииКлиентСервер`). Строка запуска и настройки отбора —
   в документации движка (`exts/yaxunit`).
3. Результат — JUnit XML; из него собирается отчёт Allure: наборы, тесты, проверки, длительности.
   Полезно смотреть не только «127 / 127 PASSED», но и сами проверки: число тестов в отчёте — это
   число проверок (с учётом вариантов, заданных `СПараметрами`), и оно может отличаться от числа
   тестовых методов (например, `ОМ_ОбщегоНазначения` — 31 метод и 51 проверка,
   `ОМ_ОбщегоНазначенияКлиентСервер` — 127 методов и 127 проверок,
   `ОМ_СтроковыеФункцииКлиентСервер` — 43 метода и 43 проверки).

Правило набора: тест принимается только если он умеет падать. Перед публикацией ожидания в тестовом
модуле инвертируются, набор обязан покраснеть целиком, после восстановления — снова позеленеть
(подробнее — [`docs/knowledge/honesty-check.md`](docs/knowledge/honesty-check.md)).

## Разработка

- Добавление тестов — в тестовый модуль `src/CommonModules/ОМ_<Модуль>` (по одному тестовому модулю на тестируемый общий модуль);
- спецификация (`docs/modules/*.md`) обновляется из исходника тестового модуля: генерируемый регион
  помечен комментариями `BEGIN:generated` / `END:generated`, ручные разделы сохраняются;
- ветвление, версии и теги — [`GIT-FLOW.md`](GIT-FLOW.md);
- что выкладывалось в `develop` — [`CHANGELOG.md`](../../CHANGELOG.md) в корне репозитория;
- нетипичные ситуации EDT и их разбор — [`docs/knowledge/`](docs/knowledge).
