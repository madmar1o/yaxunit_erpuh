## Проверка честности тестов

Честный тест обязан уметь упасть. Проверка идёт в два шага: статический аудит модуля и мутационная
проверка (инверсия ожиданий — модуль обязан покраснеть целиком).

### 1. Статический аудит

| Проверка | Результат |
| --- | --- |
| Каждый тест вызывает метод `ОбщегоНазначения` | 31 из 31 |
| Каждый тест содержит утверждения | 31 из 31 (48 цепочек `ЮТест.ОжидаетЧто`) |
| Имя теста начинается с имени проверяемого метода | 31 из 31 |
| Тесты без утверждений / без вызова метода («пустые») | не найдено |

### 2. Мутационная проверка

Ожидания инвертируются: `.Равно` ↔ `.НеРавно`, `.ЭтоИстина` ↔ `.ЭтоЛожь`, `.ИмеетТип("X")` → `.ИмеетТип("X!")`,
`.ИмеетДлину(N)` → `.ИмеетДлину(N + 1)`, `.Заполнено()` → `.ИмеетДлину(0)`. На таком модуле обязан упасть каждый тест.

| Шаг | Результат (прогон 16.10.2026 19:36) |
| --- | --- |
| Инверсия ожиданий — 69 замен | `Равно/НеРавно` 28, `ЭтоИстина/ЭтоЛожь` 19, `ИмеетТип` 13, `ИмеетДлину` 5, `Заполнено` 4 |
| Прогон инвертированного модуля | 51 проверка красная из 51 (31 failed + 20 errors), зелёных 0 → все 31 тестовых метода «убили мутанта» |
| Восстановление исходного модуля | SHA256 совпал с версией в репозитории |
| Контрольный прогон после восстановления | 51 / 51 PASSED |

20 «ошибок» вместо «падений» — следствие инверсии имени типа: `Тип("ОписаниеТипов!")` не существует,
проверка падает исключением. Для честности теста это то же убийство мутанта.

**Ограничение.** Тестируемый код — общий модуль конфигурации ERPUH, и прямая мутация продакшн-кода в него
не вносится (конфигурация на поддержке: посторонние правки недопустимы). Инверсия ожиданий доказывает,
что проверки исполняются и зависят от фактических значений, но не заменяет мутационное тестирование
кода модуля. Если тестовый модуль начнёт покрывать методы с вычисляемым результатом, честность стоит
подтверждать ещё и подменой факта (например, через мок Мокито).

| `БезопасноеВыполнениеВнешнегоКода` | `ВыполнитьМетодКонфигурации`, `ВыполнитьВБезопасномРежиме`, `ВычислитьВБезопасномРежиме` | нужен безопасный режим и внешний код |
| `БуферОбмена`, `РаботаСИнтернетом`, `ВерсионированиеПрограммныхИнтерфейсов` | `СтрокиИзБуфераОбмена`, `СоздатьWSПрокси`, `ПолучитьВерсииИнтерфейса` | внешние ресурсы и сервисы, в серверном юнит-прогоне недоступны |
| `ФункцииОпределенияТиповОбъектовМетаданных` | `ЭтоПеречисление`, `ЭтоРегистрНакопления`, `ЭтоЗадача` (покрыты `ЭтоДокумент`, `ЭтоСправочник`) | группа «близнецов»: выгодно покрыть одним параметризованным тестом |
| `Запросы`, `ДинамическийСписок`, `ПереходныеПроцедурыИФункции`, `УстаревшиеПроцедурыИФункции`, `ТекущееОкружение`, `Прочее` | `СформироватьСтрокуДляПоискаВЗапросе`, `СтруктураСвойствДинамическогоСписка`, `ЭтоОбновлениеНабораЗаписей` | часть зависит от контекста и платформы, часть устарела |

**Следующий шаг по покрытию:** параметризованный тест на группу `ЭтоХxx` (11 методов одним тестом) и чистые
функции сравнения/копирования коллекций — `КоллекцииИдентичны`, `ДанныеСовпадают`, `СкопироватьРекурсивно`,
`СравнитьМассивы`, `РазмерСтрокиВБайтах`, `ОписанияТиповПересекаются`, `ОписаниеТипаВсеСсылки`.

## Как запускать

1. **Расширения в базе.** В тестовую базу ставится движок (`exts/yaxunit`) и тесты (`exts/yaxunit_erpuh`):
   собрать `.cfe` и подключить, либо открыть исходники проектами в EDT и обновить конфигурацию базы данных.
   Тесты — серверные, без записи в ИБ, поэтому подойдёт любая копия демо-базы.
2. **Прогон.** Штатно — внешней обработкой запуска тестов YAxUnit с отбором по расширению и модулю
   (`YAXUNIT_ERPUH` / `ОМ_ОбщегоНазначения`). Из EDT то же делает `run_yaxunit_tests` на конфигурации
   запуска тонкого клиента.
3. **Отчёт.** Результат прогона — JUnit XML, из него собирается отчёт Allure: наборы, тесты, проверки,
   длительности. Сводка «51 / 51 PASSED» — это 51 проверка (с учётом вариантов `СПараметрами`),
   31 тестовый метод, 5 наборов.
4. **Честность.** Инверсия ожиданий в тестовом модуле: набор обязан покраснеть целиком (см. таблицу выше),
   после восстановления — снова зелёный. Тест, который не умеет падать, в набор не принимается.
5. **Правило репозитория.** Под каждый модуль — своя ветка, после проверки — слияние в `develop` и тег
   `0.0.0.n+1`; описание правил — `GIT-FLOW.md` в этой папке, порядок выкладки — `CHANGELOG.md` в корне
   репозитория.
